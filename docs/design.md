# Snug: design

Snug is a self-hosted data room for early-stage founders, one instance per company on the founder's own server. [docs/architecture.md](architecture.md) explains how the code works.

## 1. Decisions

| Area | Decision | Why |
|---|---|---|
| Web framework | Django 6.1. | CSRF, server-side sessions, versioned migrations, argon2id, CSP and security headers are built in and long audited. Papermark's CVEs were in its hand-written security primitives. Fewer dependencies than the Starlette path. |
| Django admin | `django.contrib.admin` is not installed | Extra attack surface, and it would not enforce TOTP. |
| Audit log | Every admin and viewer event, in an append-only table, with a filtered view and a CSV export in the admin interface. Every viewer event records the visitor's country from DB-IP's data, whether or not the link is UK-only, shown beside the address; empty when the address cannot be placed. | Each sign-in and access is recorded from the first. |
| Lost second factor | One-time recovery codes issued at enrolment; replacing your own authenticator in Settings, with the password and a code from the old one or a recovery code; any admin can reset another admin's second factor; `snug reset-2fa` on the server | A lost phone must not lock an admin out for good. |
| Forgotten password | A "Forgotten your password?" link on the sign-in page emails a one-time link that works for one hour. The reply is the same whether or not the address belongs to an admin, and the link is created and emailed in the background, so the reply does the same work, and takes as long, either way. Limited to 5 requests per IP address and 3 per email address in 15 minutes. The page that sets the new password also asks for a code from the authenticator, or a recovery code, with its own limit of 5 codes per admin in 15 minutes, so someone holding a link cannot use up the admin's sign-in attempts and lock them out. Sharing one allowance with sign-in would bring that lockout back; keeping this one to a single link's worth means someone with both the password and the mailbox gets 15 guesses in 15 minutes rather than 10, and every wrong code is audited. A bad password spends no code; a wrong code leaves the link working, and the fifth spends it. The count is kept on the link itself, so it never resets while the link works. Changing the password signs the admin out everywhere and emails them; the request, failures and the change are audited. Without email, the page has instructions to ask another admin or run `snug reset-password` on the server, an audited command that replaces Django's unaudited `changepassword`. | People forget passwords. With the second factor asked for on the reset page, someone in the admin's mailbox can neither sign in nor change the password. |
| Changing your password | In Settings, with the current password, the new one twice and a fresh code from the authenticator, under the same 10-in-15-minutes limit as confirming admin changes. The new password is checked first, so a weak one spends no code. This browser stays signed in; every other session ends. The admin is emailed and the change is audited. | The same proof as any other change to an admin account, so someone at an unlocked computer cannot change it. Signing out elsewhere ends any session a thief may hold. |
| Replacing your authenticator | In Settings, with the password and a code from the current authenticator or a recovery code, under the 10-in-15-minutes confirmation limit. The old authenticator and recovery codes stop working at once, which ends every session. The admin goes straight to the setup page for the new one, and its link is emailed too, working for 72 hours. Every admin is emailed and the change is audited. | A new phone should not need another admin. If the tab is closed halfway, the emailed link still works. The alert warns every admin in case the change is a takeover. |
| Removing admins | An admin cannot delete themselves, and the last admin cannot be deleted | Avoids locking a company out of its own instance. |
| Second factor | TOTP with a one-step window either side and replay protection (the last used step is stored). Codes must be ASCII digits. Ten recovery codes of 80 bits each, stored as SHA-256 hashes. TOTP keys stored unencrypted. | The window covers clock drift; replay protection stops a shoulder-surfed code being used twice. TOTP keys must be readable to check codes; the database stays on the founder's server, and backups are encrypted. Encrypting them would need a new dependency, its key would sit on the same server, and losing that key would wipe every admin's second factor. A stolen database copy still needs each admin's password. |
| Sign-in limits | Per address: 20 password, 20 code and 10 recovery attempts. Per account: 30 password attempts, 10 code attempts and 5 recovery attempts. All in 15-minute windows, held in SQLite so every process shares them. Each attempt is counted before it is checked (`ratelimit.allow`), so simultaneous requests cannot slip under a limit. 5 wrong codes after one correct password returns to the password step. | A low account limit would let anyone lock a founder out by typing wrong passwords, and a correct password only reaches the code step. |
| Admin sessions | A new session id at each step. Five minutes from password to code, and back to the password if the password or TOTP key changes in between. Ending after one hour idle or twelve hours absolute. The session hash covers the password and the TOTP key, so changing either signs out everywhere. | A new id at each step stops session fixation, and a new password or key ends every session without scanning the session table. |
| File handling | Uploads stream to a temporary file in the data folder, with a hash and a size limit for their kind, the kind decided by the first bytes (`%PDF-`, a zip, or an `ftyp` box), then an inspection in the worker, before a rename into `originals/<random>.pdf`, `.docx`, `.pptx`, `.xlsx` or `.mp4`. The uploaded name is kept for display only. A POST from anyone but a signed-in admin is refused over 64 KB, from its declared length, before the body is read. | The file-handling rule in the security requirements: generated names, and paths from records only. |
| Document worker | The worker reads PDFs, checks and stamps Word, PowerPoint and Excel files, checks videos, a video in pieces, and redraws the founder's logo and tab icon. `python -I -m snug.rendering.worker`, with a clean environment (no `SNUG_*`), given the file as an open file descriptor, never a path, and returning results through a pipe, which Snug reads in bounded chunks. Past 64 MB (for a stamped download, twice the upload limit or the file's size, whichever is larger, plus 1 MB) or the deadline, the worker's whole process group is killed. It limits itself to 1 GiB of memory (enforced on Linux), 60 s CPU, 64 MB written to any file and 32 open files, then confines itself with Linux Landlock (no filesystem access except reading system fonts, no TCP) and a seccomp filter that refuses to create any socket, since Landlock's network rules cover TCP only, and refuses to trace, signal, re-prioritise or change the limits of another process, or read its memory, since Landlock scopes signals only from ABI 6. All three are required: Landlock ABI 4 (Linux 6.7) or later, the filter, and the memory limit. If any fails, the worker refuses to read the file, and the upload fails with "This server cannot open documents safely". `SNUG_UNSAFE_UNCONFINED_RENDERING=true` allows unconfined reading for development on a machine without Landlock, such as macOS; Snug's system check warns whenever it is on. Timeouts are 60 s to inspect an upload or stamp a download, and 30 s to render or stamp a page. At most 2,000 pages; renders capped at 6.4 megapixels and 8,000 px a side. Snug's own processes (gunicorn and the `snug` command) mark themselves non-dumpable, so a compromised worker cannot read their `/proc` entries or environment. The worker runs as the same user as Snug and relies on Landlock and the limits above. Switching to a separate user would need Snug to hold the power to switch to any user, root included, which a compromised Snug could use. `snug doctor` reports the confinement level, from a fresh worker that confines itself and reads nothing. Before it confines itself, a worker imports what its task uses: rendering a page loads Pillow and PDFium, stamping one only Pillow, and every other task loads everything, then stamps a tiny PDF and checks a tiny workbook, which loads the modules pypdf, zipfile and expat would otherwise load on first use. The image ships Snug's code and Python's standard library compiled, since the read-only root cannot keep what a worker compiles. | A malformed or hostile PDF cannot take the server down. Even if it took over PDFium, it could not read the secret key, the database or other documents. Once confined, the worker can open no file, so a module loaded late would fail. A fresh worker starts for every page shown, so its start-up is part of every page's wait. |
| Render cache | Plain pages per version, page and width (800 or 1,600 px), as WebP, in `renders/`. Page 1 is rendered at 1,600 px in the background once a PDF is uploaded or an Office file's preview is ready; other pages are rendered on first view. | One cached page serves every viewer, and the cache can be deleted and rebuilt. |
| Stamped pages | Each page an investor is shown is stamped for their link and kept in `stamped/<day>/<link>/`, named by version, page, width and a hash of the stamp's text, until the day ends; hourly housekeeping deletes other days, and revoking a link deletes its pages. While the investor is on the landing page, before they click Open or while they fetch their code, the first two pages of a document, or page 1 of the first three documents in a room by title, are stamped for them in a background thread, which records no visit. A request for a page being stamped waits for that stamp. Every request goes through `authorise()` before a stored page is served. Not backed up. | Each stamp needs a fresh confined worker, slow on a one-CPU server, and the investor would see a blank page meanwhile. The stamp shows the date, so a page is kept no longer than a day, and only the pages an investor was shown or is about to be. |
| Audit log storage | Append-only, refused by the model, its queryset and SQLite triggers | The triggers stop even raw SQL from inside Snug changing or deleting an entry. |
| Admin invites | An emailed setup link: 256-bit token, stored as a hash, one live link per admin, working once for 72 hours. The invitee chooses a password and adds the authenticator in the browser, then sees their recovery codes once. Without email, admins are created with `snug createadmin`. | Nobody has to send a password by chat. 72 hours spans a weekend without leaving a forgotten invite open. |
| Confirming admin changes | Inviting, removing or resetting an admin asks for a fresh code from the acting admin's authenticator, used once (10 tries per admin in 15 minutes). | Someone at an unlocked laptop, or with a stolen session, cannot quietly add themselves. |
| Admin change alerts | Every active admin is emailed when an admin is invited, removed or has their second factor reset. | Every other admin hears when an admin is added. |
| Rate limiting | A small database-backed limiter of our own, not a library | Shared correctly across server processes; easy to test. |
| Client IP | `X-Forwarded-For` and `X-Forwarded-Proto` are trusted only from Caddy, which has fixed addresses on the Compose network; the Compose file sets `SNUG_TRUSTED_PROXIES` to them. From anyone else the `forwarded_proto` middleware drops `X-Forwarded-Proto`, so a plain HTTP request cannot pass for HTTPS. IPv6 is on for that network. | Rate limits, UK-only mode and the audit log all depend on the real address. Without IPv6 on the network, Docker relays IPv6 visitors through its own proxy, and they would all share one address. |
| Verification codes | Six digits, single use, ten minutes, at most five wrong attempts per code, rate limited per link, per IP and per email address. One live code per link: asking again replaces it, so checks against a live code are also capped at 50 per link per day (checks with no live code are not counted, so they cannot lock the owner out). Each try is claimed before the code is compared, so simultaneous guesses cannot exceed five. Stored only as an HMAC (keyed with the secret key) over the link's current token hash, so reissuing a link ends its code. | Without a cap per code, one code could be guessed without limit. A six-digit code hashed without a key could be recovered from a database copy in a second. |
| Viewer session lifetime | 7 days by default, set with `SNUG_VIEWER_SESSION_DAYS` (1 to 90) | Revocation is checked on every request, so a long session does not weaken it. |
| Viewer sessions | Separate from admin sessions. One `__Host-snug-viewer` cookie (HttpOnly, SameSite=Lax) holds 256 random bits; the database keeps only their hash, with one row per link the browser has opened, bound to the link, its current token and its email address, so reissuing a link ends every session for it. The cookie is replaced each time the viewer verifies. | Each link is verified and revoked on its own. Nobody can open a link with a copy of the database. With Lax, a viewer arriving from a link in an email is recognised; Strict would drop the cookie on that first request. |
| Viewer rate limits | Asking for a code: 20 attempts per IP in 15 minutes; 10 wrong addresses per link in an hour, after which every request on that link gets the same neutral reply for the rest of the hour (the right address still gets a code); 5 codes sent per link in 15 minutes; 10 codes to one inbox in an hour. Entering a code: 30 per IP in 15 minutes, five per code, and 50 per link a day. Opening a link without verification: 30 per IP in 15 minutes. Downloads: 30 per link an hour, since each stamps the whole PDF in a worker. Reading-time heartbeats: 600 per IP in 15 minutes, about ten open tabs. Each request is counted before its limit is checked (`ratelimit.allow`), so simultaneous requests cannot slip under. | The per-inbox limit stops Snug being used to flood someone's email. |
| Viewer URLs | Everything a viewer sees is under `/v/<token>`; a room link's documents are under `/v/<token>/d/<document token>`, and room membership is checked on every request, so removing a document from a room ends access to it at once. Each view is wrapped by `viewer_content` (which calls `authorise()`), by `viewer_nda` on the NDA page (`authorise()` without its NDA check) or, for the pages that start a session, `viewer_gate` (the link check, and the UK-only check, so nobody abroad is sent a code). A test walks the URL configuration and fails on any viewer view without one, on any integer parameter other than a page number or image width (positions within the document the token grants, not identifiers), on any path parameter, and on any route outside `admin/` and `v/` other than the root redirect and the founder's brand files under `brand/`. | A test enforces the single authorisation path. |
| Wrong email address | On the landing page, a wrong address gets a message that it is not the one the link was sent to, and no code is sent. After 10 wrong addresses on a link in an hour, it switches to a neutral reply for every request, so a guesser learns nothing and nobody can lock the owner out. In that mode the code is emailed in the background, so the reply's timing does not depend on the address, and a wrong code says only that it is not right, never how many tries are left. | Typos are the common case. Guessing is rate limited, and a code still needs the real inbox. |
| Links without verification | The link opens a short page with a button to open the document or room, which starts the session; nothing happens on a plain visit. | Email security scanners fetch links before people do. A visit must not start a session or count as a first open. |
| Watermark stamping | In a fresh confined worker, like rendering, once a day for each link's page (see Stamped pages): Snug passes the cached page and the font as open files, and checks only the container format of what comes back. The mark is the viewer's email address and the date, tiled diagonally at about 28% opacity, plus a footer band reading "Shared with *email*", the date and "Link *ref*". | The cached page came out of a worker that reads untrusted PDFs. Decoding it in Snug's own process would let a compromised worker attack Snug's image decoder (libwebp had exactly such a bug, CVE-2023-4863). |
| Reading time | A page is recorded as shown when the reader serves it. While the tab is visible, the reader sends a heartbeat every 15 seconds; "end" when the tab is hidden or closed, "resume" when it is shown again. Snug credits each heartbeat with the time elapsed since the last, at most 20 seconds, to the page being shown. A visit ends after 30 minutes with no events. Each new visit is audited as `viewer.document_viewed`. | The server measures time, so a browser cannot inflate it, and a sleeping laptop or a hidden tab does not count as reading. |
| NDA | Available on single-document links as well as rooms. One NDA for the whole instance, set in Settings and versioned; a room, or a link to a single document, requires it or not. Acceptance is per link and per version, recorded once for each pair: editing the NDA asks everyone to accept the new version on their next visit, and earlier acceptances stay in the history. Each acceptance records the name, email, link, time, IP address, user agent and a SHA-256 of the exact text. | A document shared on its own may need an NDA too. Most founders have one NDA. Every record matches the exact words that person agreed to, and is tied to the link it was made on. |
| UK-only mode | A link to a single document, or a room (and so every link to it), can open only for visitors in GB, Jersey, Guernsey and the Isle of Man (decided 6 November 2026), by their address in DB-IP's data. It is `authorise()`'s check 4; the gate pages check it too, so nobody abroad is sent a code, and a visitor without a session is checked before being asked to verify. It fails closed: an unknown country, or a server without the data, is refused. A refusal shows one page (403) and is audited as `viewer.outside_uk` with the country. `snug doctor` and the Overview warn when something is UK-only and the data is missing or older than last month. The link form and the room's switch include a credit to DB-IP. | Many UK funds and family offices sit in the Channel Islands. Failing open would let anyone through whenever the data was missing. A VPN gets round it, as the form's hint and `docs/security.md` say. |
| Rooms | A named collection of documents with at most one level of folders. A document can be in any number of rooms, and a link points to one document or one room. | A document is uploaded once and keeps one version history and one set of analytics, whichever rooms it is in. |
| Cover message | Optional plain text on a link, up to 1,000 characters, with line breaks kept and nothing rendered as HTML. It is at the top of the investor's *About this link* panel, and in the email with the link. | Cheap, and founders asked for it. Plain text means a message cannot contain script or a disguised link. |
| Email settings | Saved in Settings, and used from the next email, with no restart. Without them, the `SNUG_SMTP_` settings in `snug.env` are used, then the outbox on localhost. The transport (`snug.core.email_backend`) reads the settings in force when each message is sent. Passwords are stored as they are and never shown again. A saved one shows as twelve dots, the field's placeholder, so its value never reaches the browser and an empty box keeps it. Saving needs a fresh authenticator code (the 10-in-15-minutes confirmation limit), and every admin is alerted through the settings in force before the change, so a stolen session cannot quietly reroute codes and reset links. The SMTP server must be on port 25, 465, 587, 2465, 2525 or 2587 (2465 and 2587 are Amazon SES's, for DigitalOcean) and resolve only to public addresses (any, on localhost), with IPv6 ranges that contain an IPv4 address judged by the IPv4 address inside (IPv4-mapped) or refused (NAT64, 6to4, Teredo), so Snug cannot be aimed at its own network or the cloud metadata address. The check runs when saving, only after the code is confirmed, so someone with a session but no code learns nothing about internal names; and again when sending, when Snug connects to the very address it checked, while TLS still verifies the certificate against the server's name (DNS rebinding cannot slip in between). Test sends are limited to 5 per admin in 15 minutes. `snug setup` does not ask about email. The panel offers Google Workspace or another provider over SMTP, the fields for each shown by CSS alone (`:has()`). The setup is laid out as numbered steps, all on the page from the start and greyed until the one before is done (the client or SMTP server; for Google, the sending mailbox; a test). Each save, connection or error lands on the step to do next, with its notice there; Google's refusals are held in the session over a redirect to the mailbox step, so its one-time code leaves the address bar. *Clear email settings*, in the same panel as the choice of provider and under it, shown whenever anything is saved (working or not), forgets everything saved here (the client, the mailbox's permission, the SMTP details) with a fresh code, alerts every admin through the route in force before, then revokes at Google; email falls back to `snug.env`, the outbox on localhost, or off. Google Workspace sends over the Gmail API on port 443 (decided 9 November 2026), since DigitalOcean blocks the only ports Google's mail servers accept, and Google has offered no way to create an OAuth client from the command line since March 2026. The founder makes an internal OAuth client in their own Google Cloud project ([docs/email-google.md](email-google.md)), and the sending mailbox approves it for `gmail.send` alone (plus `openid email`, for its address), with PKCE. *Connect Google* is a link, since the content security policy's `form-action` would stop a form's redirect to Google; the approval is held in the session until a fresh authenticator code confirms it, then every admin is alerted through the settings in force before. The mailbox step has a note, before the trip to Google, that this second code is coming, and on the return a green notice shows the approved mailbox. Snug keeps the refresh token; access tokens are kept in memory for their hour. *Disconnect* revokes the permission at Google, and needs a fresh code too, since it turns email off. Every save, connection and disconnection compares everything that decides delivery before and after (the route, server, port, account, address, and the secrets compared in memory in constant time, since another account's password at the same server reroutes mail too), and if it changed, alerts every admin through the route before; a permission given up at Google is revoked only after that alert is out. Saving SMTP settings revokes and forgets any Google permission. Google's `code` and `state` are redacted from any logged address. An optional From address lets Snug send as another of the mailbox's addresses, such as one on a Workspace user alias domain, since Google approves the primary account; Gmail honours it only if the mailbox has it under *Send mail as*. Standard library only. Calls to Google, like DB-IP's downloads, go through `snug.core.outbound`, which takes proxy settings from the environment alone. | Founders expect to set email up in the interface, and changing it should not need a server and a restart. |
| Backups | Litestream writes the database's replica to a folder on the server; an rclone sidecar copies that folder, the uploaded originals and the branding images to the founder's bucket every 5 minutes, through an rclone `crypt` remote (XSalsa20 and Poly1305, encrypted before upload). The crypt password and salt are generated during setup, and the founder must store them. The database can be restored to any moment in the last 7 days; anything the copy would delete or overwrite in the bucket, the database replica's files included, is kept there under `deleted/<date>/` for 30 days, so the backups survive a wiped server. The sidecar records its last success in the data volume for `snug doctor`. | Litestream only replicates SQLite. The backups go to the founder's own bucket, encrypted so that only the founder can read them. Litestream 0.5 dropped its age encryption and still has no client-side encryption of its own (as of 6 November 2026); rclone's crypt covers everything with one key, at the cost of up to 5 minutes' data rather than a second's. |
| GeoIP | DB-IP IP to Country Lite (CC BY 4.0, as of 5 November 2026), as CSV, which housekeeping downloads each month (or last month's, early in a month before the new one is out) and loads into `geoip/countries.sqlite3` in the data folder: a table of ranges keyed by 16-byte addresses, IPv4 mapped into IPv6, so a lookup is one indexed query. Every row is checked as it streams in, in batches, and the new file replaces the old only once it is complete; if anything is wrong, the data in use stays, and the next try waits six hours. It is not backed up, since it can be fetched again. No new dependency: the standard library's `csv`, `gzip` and `sqlite3`, fetched through `snug.core.outbound`. Attribution in the docs and the admin interface. | Bundling it in the image would go stale. With a local copy, no visitor's address is sent anywhere. Streaming keeps the load to about 12 MB of memory; building the whole table in memory took about 420 MB, too much beside Snug on a 1 GB droplet. |
| `snug doctor` email check | Sends a code and asks the operator to type it back | Snug cannot read the operator's inbox. |
| Periodic work | `snug housekeeping`, run every hour by a thread in gunicorn's master process, each time as a fresh process. It deletes reading data past its retention period (audited as `system.reading_data_deleted`), expired codes, viewer sessions, setup links and rate-limit windows, and pages stamped on earlier days; then it runs the slower `snug doctor` checks and stores them for the Overview, fetches the GeoIP data when a new month's is out, and moves on any Office previews left waiting. It reports counts only. | The container has no cron. A fresh process keeps the master free of Django, and a failure there never touches the processes serving requests. |
| Coverage | A floor of 90% enforced in CI, and no Codecov | One fewer third-party service and token. |
| CI actions | Every third-party action pinned to a commit SHA, kept current by Dependabot | Supply-chain hardening. |
| Changelog | A plain `CHANGELOG.md` with an `[Unreleased]` section | Changelog fragments in a `changelog.d/` folder solve a throughput problem this project does not have. |
| Security headers | Strict CSP from `default-src 'none'`; `Referrer-Policy: same-origin`; `__Host-` cookies; HSTS for one year, without subdomains or preload; Permissions-Policy and Cross-Origin-Resource-Policy | Viewer URLs contain tokens, so no Referer may reach another site. `no-referrer` would make browsers send `Origin: null` on form posts, which fails CSRF. Subdomains and preload are left to the founder. |
| Logging | No request access log, in Snug or in gunicorn | Viewer URLs contain tokens. |
| Health check | `/healthz` is answered before the host check | Docker's health check probes the container by its internal address, which the host check would refuse. |
| Commit trailer | `Co-Authored-By: Claude <noreply@anthropic.invalid>` | The `.com` address resolves to an unrelated GitHub account. |
| Branding | Snug takes its palette and inspiration from the Negroni brand kit, without following it to the letter. No commercial brand fonts; Geist and Geist Mono (OFL) instead. | PP Hatton and NB Grotesk Pro Mono need commercial licences and cannot ship in an MIT repository or a public image. |
| Front end | Section 3: the Negroni palette, Geist type, Phosphor icons and the reading heatmap, in one stylesheet, `snug.css`, grown from the mockups' `docs/design/snug.css` | Close to the Negroni brand, in one stylesheet with no build step. |
| Logo | The half-glazed snug door (section 3.14) | Door, monogram and Negroni sparkle; a snug is a pub's private room. |
| Link tokens | 256-bit random tokens, stored only as SHA-256 hashes. The full link is shown once, at creation; afterwards the founder can issue a new link, which stops the old one. Each link also has a short, non-secret reference (like `L-7Q2K`) for watermarks and the audit log. | A leaked database or backup exposes no working links. |
| Office files | Excel workbooks (.xlsx), decided 9 November 2026, and Word documents (.docx) and PowerPoint presentations (.pptx), decided 12 November 2026, shared as the working file, for download, since that is what an investor needs; with the LibreOffice converter installed, investors can also read them as pages (Office converter and Office previews below). A zip's first bytes make it an Office file, and the worker reads which format from its main part; a document's versions are all one kind. The confined worker checks each upload (`snug.rendering.ooxml`, standard library only): the root relationship points to the main part, whose content type must be a plain workbook's, document's or presentation's, so templates, slide shows and macro-enabled files are refused; anything typed as VBA, Excel 4.0 macro sheets, ActiveX or OLE objects, or a Word alternative format chunk (another document, such as HTML or RTF, imported when the file opens), by override or extension default and in any case, is refused, as is any relationship to such code, any part in the old compound format that OLE objects and .doc, .ppt and .xls files use, a part or extension typed twice, part names that repeat or differ only in case, an encrypted part, more than 10,000 parts or more than 1 GiB unpacked by the zip's index. An Office file inside another, such as the workbook that holds a chart's data, opens in Excel when the chart's data is edited, so it is checked as an upload is. That covers any part a package relationship points to and any part that is a zip, whatever its name or type: at most 32 of them, each up to 64 MB, within the upload's 1 GiB. An Office file inside an embedded one is refused. Any relationship other than a hyperlink whose target is on another computer (a URL, a UNC path, or a file URL with a host) is refused, decided 12 November 2026: Office fetches a remote template, frame, picture or object when the file opens, which can deliver malware or leak a Windows password hash. A template on the author's own disk, which Word records in most documents, is allowed. A relationship typed as a hyperlink may point anywhere, so only a hyperlink element may use it; a picture or object that points to one is refused. Every XML part of every Office file, whatever its folder, is read once in a stream, since Office finds parts by relationship rather than by path. In a Word document it is read for fields: DDE and DDEAUTO, which start another program, are refused, as are INCLUDEPICTURE, INCLUDETEXT, INCLUDE, LINK and IMPORT fields that point at another computer, quoted or not. A field with another field inside its instruction is allowed only if its keyword is already written in full and is one of the few that compare, calculate or set text (IF, COMPARE, =, QUOTE, SET, ASK, FILLIN, SKIPIF and NEXTIF, as a mail merge uses); otherwise its keyword or address could be built at update time, so it is refused. Every part typed as XML, or whose bytes begin as XML whatever its declared type, is read; only pictures are skipped, since an SVG often has a DOCTYPE. A workbook's DDE and OLE links to another program are refused too (decided 12 November 2026). XML is parsed with expat behind handlers that refuse any DOCTYPE or entity declaration, in any encoding. A workbook's visible sheets are listed, to investors and admins, and a presentation's slide count is read from its own list of slides; a presentation with none, or a workbook with no visible sheet, is refused. Each download is stamped for its reader in the worker. The comments (above the founder's own) and three custom properties hold the reader's email address, the date and the link, and every other part is streamed through unchanged, so formulas, charts, slides and styles survive. Nothing in the content is added or changed to show who it was shared with (decided 9 November 2026). ## 3. Front end

The design draws on the Negroni brand.

### 3.1 Design read

An admin tool for founders and a reader for investors, in the Negroni palette, built from native CSS and server-rendered HTML.

Layouts are orderly and aligned, the only motion is hover and press feedback, and the viewer is sparser than the admin.

### 3.2 Principles

- **The viewer belongs to the founder.** It uses plain neutrals with their accent colour and their logo, and no Snug or Negroni branding. The admin is Snug's own, in the Negroni palette.
- **Server-rendered first.** Every page works as plain HTML forms and links. JavaScript only enhances.
- **The strict CSP shapes the design.** No inline scripts, no `style=""` attributes and no third-party origins (section 3.10).
- **Accessible by default.** WCAG 2.2 AA throughout, with tests where possible.
- **Copy.**
  - British English, plain and low-drama, in sentence case.
  - Form labels sit above their fields, with errors below them.
  - No em or en dashes in interface text, and no middle dots used as separators.
  - Missing values are written in words ("No expiry"), never shown as a dash.
  - Figures come from real data, never invented precision.
  - No exclamation marks and no emoji.

### 3.3 Typography

- **Geist and Geist Mono** (SIL Open Font Licence 1.1), self-hosted as variable WOFF2 files: 70 KB and 72 KB.
  - Pinned to release v1.8.2.
  - Loaded with `font-display: swap`, and the sans is preloaded.
  - The fallback is the system stack, so the page works before the font arrives.
- **Weights follow the brand.** Negroni sets display text in light weights, so page titles and large figures use Geist Light (300) at 2.1rem. Section headings are Medium (500) at 1.1rem. Body text is Regular at 15px. Labels are Medium at 0.875rem, in sentence case rather than spaced capitals.
- **Mono for details**, as the brand uses NB Grotesk Mono for metadata. Geist Mono is reserved for identifiers, page counters, link IDs, copied links and the watermark.
- **Tabular figures** wherever numbers line up.
- **No serif.** PP Hatton cannot be licensed for an open-source project, and a substitute serif in a product UI would read as decoration.

### 3.5 Shape, depth and motion

- **One radius rule.** 8px on everything rectangular (buttons, inputs, panels). 4px on small inline labels. 2px on document pages, so they read as paper.
- **No shadows except under the document page** in the reader.
- **No decorative dots.** Status labels are tinted text ("Active", "Expired", "Revoked").

### 3.7 Admin interface

### 3.10 Front-end architecture

- **Templates.** Django templates with `{% include %}` partials. No front-end framework and no build step.
- **Stylesheets.** One stylesheet, `snug.css`, holds the tokens and components for the admin and the viewer, and a generated `/brand/brand.css` sets the founder's colour on viewer pages. Static files are fingerprinted by `ManifestStaticFilesStorage` and served by whitenoise. Fonts and icons are served from the instance.
- **Charts.** Server-rendered inline SVG. Geometry is set by attributes, which the CSP allows, and colour comes from CSS classes. The reading grid's chart and per-viewer strips share one coordinate system of at least 18 slots, which keeps them aligned at any width.
- **JavaScript**, as separate files: `theme-init.js` (blocking, tiny, in `<head>`), then deferred `theme.js` (the toggle), `admin.js` (copy buttons, the tabs on a narrow screen, upload progress, and asking for an Office file's Preview panel while it is made), `viewer.js` (the reader's keys and page picker, fetching the next page, and reading-time heartbeats sent only while the tab is visible, from the reader and an Office file's card), `about.js` (closing *About this link* on Escape or a click elsewhere), `video.js` (the video player's parts, heartbeats and full screen), `reveal.js` (showing a password), `brand.js` (the colour picker and its preview) and `nda-first.js` (the box for writing the first NDA). Every page works without JavaScript.
- **CSP.** `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; media-src 'self'; font-src 'self'; connect-src 'self'; manifest-src 'self'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'; object-src 'none'`. The default is `'none'`, so anything not listed is refused.

### 3.11 Empty, loading and error states

- **Empty.** An empty list has a line on what will appear there and how to start. For example: "No documents yet" and "Upload a PDF, a Word, PowerPoint or Excel file, or an MP4 video to get started", above the upload button. Or: "Nobody has opened this document yet. Reading time appears here once someone does."
- **Loading.** The reader reserves each page's exact size from stored dimensions, so nothing moves while it loads, and shows "Loading page 3" in the space until the page arrives. No spinners. The next page is fetched once the current one has arrived, so the two never compete on a one-CPU server. An upload shows its progress as a bar on the form, then "Checking the file" while the server reads it, with the button disabled throughout. A large PDF takes a while, and a page that seems to do nothing gets clicked again or abandoned. Without JavaScript the form posts as before.
- **Errors.** Shown inline, beneath the field they concern, saying what to do next. Whole-page errors (an unavailable link, a failed upload) use the same layout as the rest of the page.
- **Passwords.** Every password box has an eye at its right that shows or hides what is typed, for phones where autocorrect makes typing hard. The button appears only once its script has run, and the box turns off autocorrect, capitalisation and spellcheck. A form never submits with the password showing. A saved password or secret, which Snug never sends back, shows as twelve dots in its empty box, so the box does not look unset.
- **Saved.** Every admin save is confirmed. The page returns to the section the save was made in, with a green notice there saying what changed: "Saved. Links to this room no longer ask for the NDA." Shown once; a reload does not repeat it, except in Settings, whose notices come from the address (`?saved=`). A failed save shows its error in red in the same place.

### 3.12 Testing the front end

- **Template tests:**
  - every page sends the CSP header;
  - no template has an inline script, a `style=""` attribute or an `on*=` handler;
  - every posting form has a CSRF token;
  - no template contains an em dash, an en dash or a middle dot.
- **A contrast test** (`tests/test_contrast.py`) reads the token stylesheet, takes both sides of each `light-dark()` pair, blends the translucent tints over the surfaces beneath them, and fails any text pairing below 4.5:1, for both the admin and the viewer palettes. The founder's accent shades are tested for any colour in `tests/test_brand_colour.py`.
- **Real clicks.** Screenshots miss dead click paths. Playwright (Apache-2.0) runs the investor's journey end to end in CI, with *About this link*, a room's folders and the next page fetched after the current one, along with the admin controls that only a click can prove: the theme toggle, the password eye, the box for the first NDA, on a room and on the link form, adding a document to a room, renaming a document, upload progress and refused uploads, the email steps and clearing them, the shared columns of every admin list, a workbook and a presentation uploaded, shared and downloaded, an Office preview arriving while the description is typed, turning previews off, a video uploaded and played with its mark over it, and every admin page at phone width.

### 3.13 Settled questions

1. **Link tokens are stored hashed.** The founder sees the full link once, at creation, and can afterwards send a new link, which stops the old one working.
2. **Page images and accessibility.** Pages are images, which a screen reader cannot read, so a screen reader user downloads the file, which links allow by default. [using-snug.md](using-snug.md) says so for founders; the reader does not repeat it on every page.
3. **No thumbnails in the reader.**
4. **Playwright runs in CI**, in a real browser.
5. **A privacy notice for viewers.** Under UK GDPR the founder is the controller of investors' personal data: email address, IP address and reading behaviour. *About this link* has a short statement of what is recorded, with an optional link to the founder's own privacy policy, set in Settings.
6. **The logo and forks.** The logo files are MIT with the code, and `TRADEMARKS.md` asks that forks distributed as their own product use a different name and icon.
7. **How long reading data is kept.** Visits and time per page are deleted automatically a set number of months after their link is revoked or expires: 12 by default, set in Settings from 1 to 120, since some sectors, such as healthcare, need seven years. While a link works, its reading data is kept. The link and the audit log stay.

### 3.14 Logo

The Snug icon is a **half-glazed snug door**. A snug is the small private room in a British pub, which suits a private room for documents and a studio named after a cocktail.

- **Construction.** It is drawn on a 200 by 200 grid in the manner of the Negroni glyph:
  - a square-topped door standing on a threshold, in round-ended 13-unit strokes;
  - a glass pane with a lowercase s cut out of it, as pub snug doors had their name etched in the glass. The cut-out is an SVG mask, so the glyph works on any background;
  - a knob, which keeps it reading as a door at small sizes;
  - the four-pointed Negroni sparkle at the top left.
- **Colourways.** Campari tile with a cream (Vermouth 100) glyph is the primary. Vermouth 500 with a Campari glyph is for dark backgrounds, and Citrus 300 with a Vermouth glyph for bright ones.
- **The lockup.** A square tile, then "Snug" in Geist SemiBold, as the Negroni site sets its own tile beside its wordmark. In the admin header the tile is 40px. The tile is square, an exception to the radius rule, to match Negroni's.
- **Sizes.** The full icon holds down to 32px. The favicon is a simplified drawing for 16 and 32px: no sparkle and no s, heavier strokes, and the door enlarged to fill the tile.
- **Where it appears.** The admin interface, the admin's browser tab, the README and the GitHub social preview. Never on viewer pages, which use the founder's logo and tab icon.
- **Inline use.** The glyph takes `currentColor`. Each inline copy on a page needs its own mask id, so the `{% logo_tile %}` tag takes a suffix.
- **Files** are in `docs/design/logo/`:
  - `snug-glyph.svg`, the glyph alone;
  - `snug-icon-campari.svg`, `snug-icon-vermouth.svg` and `snug-icon-citrus.svg`;
  - `favicon.svg`;
  - `index.html` shows them as browsers load them, and `concepts.html`, built by `build_concepts.py`, contains the eight concepts the icon was chosen from.

  The favicon is SVG.

## 4. Deployment and releases

**The image.** `ghcr.io/negroni-venture-studios/snug`, public, for amd64 and arm64, built by the `Image` workflow from the Dockerfile: Python 3.14 slim, pinned by digest, with one unprivileged `snug` user, and Landlock active inside it.

| Event | Image tags |
|---|---|
| A merge to `main` | `:edge` |
| A version tag, `vX.Y.Z` | `:X.Y.Z` and `:latest` (decided 5 November 2026) |
| A release candidate's tag, `vX.Y.Z-rc.N` | `:X.Y.Z-rc.N` only, so `:latest` stays on the last release |

The workflow builds each image with its version, or `edge`, in `SNUG_BUILD_VERSION`, and its commit in `SNUG_BUILD_COMMIT`. `image smoke test`, a required check on `main`, builds the image and runs the Compose deployment, checking HTTPS from Caddy, that a forged `X-Forwarded-For` is not believed, the worker in the hardened container, backups reaching the bucket encrypted, `snug doctor`, and restores onto a wiped server and onto one where Snug never started.

**Compose.** `deploy/compose.yaml` runs Snug behind Caddy, with Litestream and the rclone backup sidecar ([docs/deployment.md](deployment.md)). A release's Compose file has that release's image (`SNUG_IMAGE` overrides it), so the deploy files at a tag run the image built from it. `tests/test_release.py` holds the image's version to `pyproject.toml`'s, and requires a dated section for it in `CHANGELOG.md`.

**A new server.** `deploy/cloud-init.yaml` prepares a fresh Ubuntu 24.04 LTS server, such as a DigitalOcean droplet: Docker from Docker's signed repository, with the signing key in the file rather than fetched from a keyserver, automatic security updates, a firewall for SSH, HTTP and HTTPS, a 1 GB swap file used only under memory pressure (`vm.swappiness` 10), the deploy files, and the `snug` command in `/usr/local/bin`. The founder then runs `sudo snug setup` in the droplet's web console or over SSH. It asks for the domain, the company's name, whether to show Office files in the browser, and the bucket on the server, so no secret is stored with DigitalOcean (decided 6 November 2026). It stops if Docker is missing, and until setup has run the login message says either that the installation did not finish or to run `sudo snug setup`. It generates the backup encryption's password and salt, asks the founder to type `saved` once they are stored, then clears the screen and the terminal's scrollback. On a server without Snug's data, it asks whether this is a restore; if so, it takes the saved `rclone.conf` pasted at the prompt (decided 11 November 2026), or uses one already in `backup/`, and restores the backups instead of starting afresh. Run again, `snug setup` keeps an existing `backup/rclone.conf`. CI validates the cloud-init file with `cloud-init schema` and the scripts with shellcheck.

**Which deploy files a server runs.** cloud-init and `snug update` fetch the deploy files of the newest release, at the tag GitHub's `releases/latest` redirects to. If that lookup fails, they stop rather than fall back to `main`, which holds code that has not been released. `SNUG_REF` makes `snug update` fetch another branch or tag. `snug update` downloads the same files as cloud-init and replaces them only once every one has arrived, never touching `snug.env` or `backup/`. It then installs the new `snug` command, pulls the images and restarts what changed. Snug applies any migrations as it starts.

**The running version.** `snug.core.version` reads `SNUG_BUILD_VERSION` and `SNUG_BUILD_COMMIT`. The Overview shows it under the status line: "Snug 1.0.0" for a release, "Snug edge, commit" and the commit's first seven characters, linked to it on GitHub, for an edge build, and the package's version "from source" for a checkout. Settings links each section to the guides at the running release's tag, or on `main` for anything else, so a founder on an older release reads the guides for that release.

**Checks.** `snug doctor` reports on:
- housekeeping: a problem when `snug housekeeping` has not completed in the last three hours (each success is recorded in the `SystemCheck` table);
- the latest backup: a problem after 15 minutes;
- the document worker's confinement level;
- DNS;
- HTTPS and the certificate's expiry: a problem with under 14 days left, since Caddy renews at 30;
- email: how it is sent, and, given an address, a test email with a code for the operator to type back;
- the country data, when anything is UK-only;
- the Office converter, when it is installed: whether it is running, and whether a newer image is waiting.

The Overview's status line shows any problem it would report (section 3.7).

**Restoring.** `snug restore` fetches the bucket's backups, rebuilds the database with Litestream (the latest, or `--at` a moment in the last 7 days), and moves any data it replaces aside rather than deleting it ([docs/backups.md](backups.md)). Each instance has a random identity, kept in the bucket from its first backup. The backup sidecar refuses to copy into a bucket holding another instance's backups, so a new server started before its restore cannot overwrite them.
